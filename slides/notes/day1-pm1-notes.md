## 1장 · 오전의 AI Agent 를 고도화하려면 어떤 기능들이 필요할까?

**말할 것**

오전에 우리는 프레임워크 없이 Agent 를 직접 구현했습니다. 모델을 부르고, 도구 요청이 오면 실행해서 돌려주고, 다시 부르는 루프였습니다. 이 루프는 잘 돕니다. 실제 제품들도 이런 루프를 직접 구현해서 많이 씁니다.

그런데 이 Agent 에 기능을 하나씩 더한다고 해 봅시다. 담당자 승인을 받고 싶다, 갈림길이 늘어난다, 중간에 프로그램이 죽어도 이어 가고 싶다, 지금 어디쯤 왔는지 보고 싶다. 그러면 루프 바깥에 직접 구현해야 할 것들이 하나씩 늘어납니다. 저장하고 다시 불러오는 코드, 쌓이는 if 문, 단계마다 저장하는 코드, 로그를 찍는 코드입니다.

직접 구현해도 됩니다. 다만 이 기능들을 미리 만들어 둔 도구들이 있고, 그중 하나가 오늘 오후에 배울 LangGraph 입니다.

**주의**

- "LangGraph 를 써야만 한다" 고 말하지 않는다. 루프는 버틴다. 늘어나는 건 그 주변 기능이다

## 2장 · LangGraph 는 무엇인가?

**말할 것**

LangGraph 는 LangChain 이라는 회사가 만든 오픈소스입니다. Python 과 TypeScript 둘 다 있고, 오늘은 TypeScript 판인 LangGraph.js 를 씁니다. 같은 회사의 LangChain 이라는 라이브러리와 이름이 비슷하지만 별개입니다. LangGraph 만 따로 쓸 수 있습니다.

공식 사이트는 스스로를 "agent runtime and low-level orchestration framework" 라고 소개합니다. Agent 의 흐름, 그러니까 무엇을 어떤 순서로 하고 어디서 갈라지고 언제 멈출지를 정하고, 그걸 실행해 주는 도구라는 뜻입니다.

공식 사이트가 내세우는 기능은 네 가지입니다. 진행 상황 보기, 사람 개입, 멈췄다 이어 가기, 기억. 오늘 오후 네 시간에 걸쳐 하나씩 다룹니다.

**Academy 에서** (L1)

- LangChain 은 LLM 애플리케이션을 쉽게 만들려고 하고, Agent 는 그중 가장 인기 있지만 **믿을 만하게 만들고 배포하기는 어렵다**. 이게 LangGraph 를 만든 동기다
- LangGraph 는 LangChain 패키지와 별개다. 핵심 철학은 Agent 흐름에 **정밀함과 통제력**을 더하는 것
- LangChain 은 모델 · 벡터 저장소 같은 연결 부품을 주고, LangGraph 안에서 같이 쓸 수 있다. 하지만 **LangChain 없이 LangGraph 만 써도 된다**

**우리 예로 바꾼 것**

- Academy 는 모델 호출에 LangChain 의 ChatOpenAI 를 쓴다. 우리는 오전에 만든 `chat()` (fetch) 를 그대로 쓴다. 그래서 오늘 새로 배우는 건 LangGraph 하나다

## 3장 · 영어 공부를 돕는 AI 를 상상해 보자

**말할 것**

예를 하나 들어 보겠습니다. 학생이 쓴 영어 글을 넣으면 피드백을 돌려주는 AI 를 만든다고 상상해 봅시다.

가장 단순한 방법은 LLM 하나에 글을 넣고 "문제점을 알려 줘" 라고 하는 겁니다. 그런데 이렇게 하면 할 때마다 결과가 달라지고, 문법 · 어휘 · 구성을 한 번에 다 보라고 하니 꼼꼼한 분석이 어렵습니다. LLM 하나로는 한계가 있습니다.

**Academy 에서** (L1)

- LLM 혼자서는 한계가 있다. **도구에 접근할 수 없고, 문서 같은 바깥 자료도 없고, 여러 단계의 일을 혼자 하지 못한다**
- 그래서 많은 LLM 애플리케이션은 LLM 호출 앞뒤에 단계를 둔다. 도구 호출일 수도 있고, 자료를 찾아오는 단계일 수도 있다

---

## 4장 · 단계로 나눈다 — 체인

**말할 것**

그래서 일을 단계로 나눕니다. 먼저 글을 분석하고, 분석 결과로 교수안을 세우고, 교수안대로 가르칩니다. 이렇게 정해진 순서로 단계를 이어 붙인 것을 체인이라고 부릅니다.

각 단계 안에서는 LLM 을 씁니다. 하지만 다음에 어느 단계로 갈지는 제가 코드로 정해 둡니다. 그래서 매번 같은 길로 가고, 믿을 만합니다. 대신 문법을 묻든 발음을 묻든 똑같은 길로만 갑니다.

**Academy 에서** (L1)

- LLM 호출 앞뒤의 단계들이 이어진 흐름을 **체인**이라고 부른다
- 체인의 좋은 점은 **믿을 만하다**는 것이다. 호출할 때마다 같은 흐름이 돈다
- 하지만 문제에 따라 **스스로 단계를 고르는** LLM 시스템이 필요할 때가 있다

**주의**

- 체인도 LLM 을 쓴다. "LLM 을 쓰면 Agent" 가 아니다. 다음 갈 길을 누가 정하느냐가 기준이다 (다음 장)

---

## 5장 · LLM 이 다음 길을 고르기 시작하면 — Agent

**말할 것**

이번엔 학생 글이 일반 이메일인지, IELTS 시험 답안인지에 따라 다른 분석기가 필요하다고 해 봅시다. 이메일은 용건과 격식을 보고, IELTS 는 채점 기준으로 봐야 합니다.

어느 분석기로 보낼지를 모델에게 맡깁니다. 갈림길 딱 하나만 모델이 고릅니다. 그런데 LangGraph 에서는 바로 여기서부터를 Agent 라고 부릅니다. LLM 이 다음 갈 길을 정하기 시작하면 Agent 입니다. 갈림길 하나만 맡는 이 가장 작은 Agent 를 라우터라고 부릅니다.

**Academy 에서** (L1)

- Agent 의 간단한 정의: **흐름을 LLM 이 정하는 것**. 체인은 개발자가 정한 고정된 흐름, Agent 는 LLM 이 정한 흐름
- Agent 에도 여러 종류가 있다. LLM 에게 맡기는 통제권을 **낮게부터 높게** 조절할 수 있다
- 낮은 쪽 끝이 **라우터**다. LLM 이 흐름의 한 단계만, 정해진 몇 개 중에서 고른다

**주의**

- 오전의 Agent 정의("결과를 보고 다시 고르는 시스템")보다 넓다. "라우터는 루프가 없는데 왜 Agent 냐" 고 물으면: Academy(LangGraph)는 "LLM 이 흐름을 정하면 Agent" 라는 넓은 정의를 쓴다고 답한다

---

## 6장 · 도구를 쥐여 준다 — 도구 호출

**말할 것**

이제 티처에게 도구를 쥐여 줍니다. 발음을 읽어 주는 도구, 단어 뜻을 찾는 도구, 화면에 밑줄을 긋는 도구입니다. 티처는 필요할 때 도구를 부르고, 결과를 보고 가르칩니다.

오전에 봤듯이 도구는 무엇이든 될 수 있습니다. 정보를 찾아오는 것, 화면에 보여 주는 것, 계산하거나 실행하는 것, 무언가를 바꾸거나 보내는 것, 사람에게 묻는 것. 모델은 어떤 도구를 언제, 무슨 값으로 부를지를 정합니다.

대신 교수안은 처음 한 번 세운 그대로입니다. 학생이 못 따라와도 계획을 바꾸지는 못합니다.

**우리 예로 바꾼 것**

- Academy L1 의 단계 설명에는 "도구 호출 Agent" 라는 단계가 따로 없다. 라우터와 완전 자율 Agent 사이를 우리가 오전 강의의 흐름(도구 → 루프)에 맞춰 한 칸 더 나눴다
- "도구는 무엇이든" 은 오전 20장의 다섯 범주 (찾아오기 · 보여 주기 · 계산 · 실행 · 바꾸기 · 보내기 · 묻기 · 맡기기) 와 같은 이야기다

---

## 7장 · 다음 단계까지 맡긴다 — 자율 Agent

**말할 것**

끝으로, 다음 단계까지 전부 맡겨 봅니다. 진행 티처가 정해진 교수안을 따라가지 않습니다. 학생에게 확인 질문을 던지고, 대답을 보고 이해도를 판단하고, 못 따라오면 플래너를 다시 불러 교수안을 고칩니다. 필요하면 문법 티처나 발음 티처를 부르기도 합니다.

그래서 같은 수업인데도 학생 A 는 네 단계 만에 끝나고, 학생 B 는 여덟 단계가 걸립니다. 단계 수를 모델이 정하니까, 계속 길어질 수도 있습니다. 유연하지만 예측하기 어렵습니다.

**Academy 에서** (L1)

- 반대쪽 끝은 **완전 자율 Agent** 다. 주어진 선택지 중에서 아무 순서로나 단계를 고르고, 심지어 다음 단계를 **스스로 만들어 내기도** 한다

---

## 8장 · 맡길수록 유연하지만, 믿기 어려워진다

**말할 것**

지금까지 본 걸 그림 하나로 정리하겠습니다. 가로축은 모델에게 흐름을 얼마나 맡기느냐, 세로축은 결과를 얼마나 믿을 수 있느냐입니다. 체인에서 라우터, 도구 호출, 자율 Agent 로 갈수록 유연해지지만, 믿을 수 있는 정도는 떨어집니다.

LangGraph 가 노리는 것은 이 곡선을 덜 떨어지게 하는 것입니다. 꼭 정해야 할 길은 코드로 고정하고, 모델에게는 필요한 갈림길만 맡기는 방식으로요.

**Academy 에서** (L1)

- 실제로 부딪히는 문제: LLM 에게 주는 통제권(가로축)을 늘릴수록 애플리케이션의 **신뢰도(세로축)가 떨어진다**
- LangGraph 는 이 **신뢰도 곡선을 휘게** 하려는 것이다. LLM 에게 더 많이 맡겨도 신뢰도를 지키게
- 많은 애플리케이션에서 개발자의 판단과 LLM 의 통제를 섞고 싶다. 늘 고정할 단계는 고정하고, LLM 은 원하는 지점에만 끼워 넣는다

**주의**

- 곡선은 Academy 의 개념 그림이다. 측정한 데이터가 아니다. "휘게 한다" 를 단정하지 않고 "노리는 것" 으로 말한다

---

## 9장 · 그래서 Graph 다

**말할 것**

이 흐름들을 그릴 때 우리는 계속 같은 그림을 썼습니다. 할 일은 동그라미나 네모, 다음 갈 곳은 화살표. 이게 그래프입니다. 할 일을 노드, 화살표를 엣지라고 부릅니다. 실선은 코드가 정한 길, 점선은 모델이 고르는 길입니다.

오전에 만든 정비 부품 Agent 도 그래프로 그리면 이렇게 됩니다. agent 가 모델을 부르고, 도구를 원하면 tools 로, 결과를 들고 다시 agent 로, 끝이면 End 로.

LangGraph 는 이 그래프를 설계하고 실행하는 데 필요한 기능들을 쉽게 구현할 수 있도록 제공합니다.

**Academy 에서** (L1)

- 이런 흐름은 그래프로 표현한다. **노드는 애플리케이션의 단계**다. 도구 호출일 수도, 자료를 찾는 단계일 수도 있다. **엣지는 노드 사이의 연결**이다
- 노드와 엣지를 어떻게 배치할지는 자유롭다

## 10장 · LangGraph 가 제공하는 기능

**말할 것**

1장에서 본 네 가지를 다시 보겠습니다. 멈췄다 이어 가기, 갈림길 처리, 단계마다 저장, 진행 상황 보기. LangGraph 에서는 이것들이 이미 들어 있습니다. 갈림길은 조건부 엣지 선 하나이고, 저장은 단계마다 State 를 남기는 저장소가 맡고, 진행 상황은 노드가 끝날 때마다 흘려 보여 줍니다. 바탕에는 모든 노드가 같이 보는 State 한 장이 있습니다.

다만 LangGraph 가 모델을 더 똑똑하게 만들어 주지는 않습니다. 오전에 직접 구현한 하네스를 정리해 줄 뿐입니다.

**Academy 에서** (L1)

- LangGraph 의 기둥: **persistence (저장) · streaming · human-in-the-loop · controllability (통제)**. 이 기둥들이 이후 모듈의 뼈대다
- LangGraph 에는 그래프를 눈으로 보며 디버깅하는 IDE, **Studio** 도 있다 (15장)

## 11장 · 시연: 가장 간단한 그래프 — `demo/graph-basics.ipynb`

**말할 것**

이제 코드로 아주 작은 그래프를 하나 만들어 보겠습니다. 앞에서 본 영어 튜터의 첫 단계, 이메일이냐 IELTS 답안이냐를 가르는 그래프입니다. 이번엔 LLM 없이, 길도 규칙 한 줄로 고릅니다. LangGraph 의 부품 세 가지, State 와 노드와 엣지가 어떻게 생겼는지만 보겠습니다.

**Academy 에서** (L2)

- 노드 세 개와 END 로 된 그래프를 만든다. START 에서 node 1 로 가는 선은 **보통 엣지(normal edge)**, node 1 에서 2 또는 3 으로 갈라지는 선은 **조건부 엣지(conditional edge)**
- 이 간단한 그래프가 LangGraph 의 핵심 부품을 보여 주는 좋은 출발점이다

**우리 예로 바꾼 것**

- Academy 는 50 : 50 동전 던지기로 길을 고른다 (기분 좋음 / 슬픔). 우리는 "Dear · Hi · Hello 로 시작하면 이메일" 규칙을 쓴다. 노트북 진행 대본은 노트북 안의 설명 칸에 있다

## 12장 · State: 노드들이 같이 보는 칸

**말할 것**

먼저 State 입니다. State 는 그래프의 노드와 엣지 사이를 오가는 값입니다. 노드에서 노드로 건네지는 공책 한 장이라고 생각하시면 됩니다. 우리 예에서는 칸이 두 개입니다. 학생이 쓴 글 text, 그리고 지나간 노드를 적어 두는 log.

log 에는 합치는 규칙, reducer 가 붙어 있습니다. 노드가 값을 돌려주면 덮어쓰지 말고 이어 붙이라는 뜻입니다. LangGraph 는 기본적으로 덮어씁니다. 그래서 쌓아야 하는 칸에는 규칙을 적어 줍니다. 자세한 건 오후 ② 에서 봅니다.

**Academy 에서** (L2)

- State 는 그래프의 노드와 엣지 사이로 **건네지는 객체**다. 여기서는 키 하나(`graph_state`)를 가진 단순한 딕셔너리
- 노드는 State 의 값을 받아, **새 값으로 덮어쓴다**

## 13장 · 노드: State 를 받아, 바꾼 칸만 돌려주는 함수

**말할 것**

노드는 그냥 평범한 함수입니다. State 를 받아서, 바꾸고 싶은 칸만 돌려줍니다. classify, analyze_email, analyze_ielts 세 개를 만들었고, 지금은 무엇을 하는지 한 줄 찍고 log 에 자기 이름만 남깁니다.

중요한 건, 어느 노드도 다음에 어디로 갈지를 모른다는 점입니다. 그건 엣지가 정합니다. 그래서 노드는 하나씩 따로 바꾸고 시험할 수 있습니다.

**Academy 에서** (L2)

- 노드는 **평범한 Python 함수**다. State 를 받아, 키 값을 꺼내 쓰고, 새 값을 돌려준다
- 노드도 함수, 조건부 엣지도 함수. 노드는 State 를 바꾸고, 조건부 엣지는 **다음에 갈 노드**를 알려 준다

---

## 14장 · 엣지로 연결하기: 다음 갈 곳을 정한다

**말할 것**

마지막 부품, 엣지입니다. 조건부 엣지도 함수 하나입니다. State 를 보고 다음에 갈 노드의 이름을 돌려줍니다. 우리 decide 함수는 글이 Dear 로 시작하면 analyze_email, 아니면 analyze_ielts 를 돌려줍니다.

이제 StateGraph 에 State 를 넣고, 노드를 올리고, 선을 잇습니다. addEdge 는 실선, 무조건 저기로. addConditionalEdges 는 점선, 함수에게 물어보고 갑니다. START 와 END 는 이름이 정해진 특별한 노드입니다. compile 을 하면 빠진 선이 없는지 한 번 검사합니다.

다 만들면 invoke 로 처음 State 를 넣어 돌립니다. invoke 는 그래프를 끝까지 돌리고, 마지막 State 를 돌려줍니다.

**Academy 에서** (L2)

- 엣지는 노드를 잇는다. **보통 엣지**는 늘 같은 곳으로, **조건부 엣지**는 우리가 정한 조건으로 고른다. 지금은 장난감 예제라 반반 확률이지만, 실제로는 **State 를 보고 판단해서** 다음을 고른다
- `StateGraph` 에 State 를 넣어 builder 를 만들고, 노드를 더하고, START 에서 보통 엣지, node 1 에서 조건부 엣지, node 2 · 3 에서 END
- **compile 은 기본적인 검사**를 한다. 그리고 그래프 그림을 그려 볼 수 있다. 점선이 조건부 엣지다
- 그래프는 LangChain 부품들과 같은 실행 규약(Runnable)을 따른다. 그중 하나가 **invoke** 다. 처음 State 를 넣으면 그래프가 돈다
- invoke 는 그래프를 **동기적으로** 돌린다. 각 단계가 끝나길 기다렸다가 다음으로 간다. 다 돌면 **모든 노드를 거친 뒤의 State** 를 돌려준다

## 17장 · Chain: 노드 하나가 LLM 을 부른다 — 노트북 ①

**말할 것**

이제 그래프 안에 LLM 을 넣어 보겠습니다. 세 가지가 합쳐집니다. 메시지, 모델, 그리고 도구입니다.

먼저 메시지입니다. 모델과는 메시지로 이야기합니다. 오전에 messages 배열을 만들어 보냈던 것과 같습니다. 이 메시지 목록을 그대로 State 에 담습니다. 그런데 State 는 기본적으로 덮어쓴다고 했죠. 대화는 덮어쓰면 안 되고 쌓여야 합니다. 그래서 messages 칸에 이어 붙이는 reducer 를 답니다.

다음은 도구입니다. 모델을 바깥 기능에 연결하고 싶을 때가 있습니다. 예를 들면 특정 입력을 넣어야 돌아가는 API 같은 것들입니다. 도구 설명을 모델에게 알려 주면, 모델은 자연어를 받아서 그 도구를 돌리는 데 필요한 입력을 만들어 줍니다. 오전에 봤듯이 도구는 검색이든, 화면 표시든, 계산이든 무엇이든 될 수 있습니다. 여기서는 단어 뜻을 찾는 lookup_word 하나만 씁니다.

그래프는 노드 하나입니다. START 에서 tutor, tutor 에서 END. 결론을 어떻게 쓰냐고 물으면 모델은 바로 답합니다. 단어 뜻을 찾아 달라고 하면, 답 대신 도구 요청을 돌려줍니다. 그런데 그래프에는 그 요청을 실행할 노드가 없습니다.

**Academy 에서** (L4)

- 체인은 몇 가지 핵심 개념을 합친다: **채팅 메시지, 채팅 모델, 도구 묶기(bind tools), 도구 호출 실행**
- 채팅 모델은 **메시지와 주고받는다**. 메시지 목록을 넘기면 AI 메시지가 나온다. 내용(content)과 함께 토큰 수 · 모델 이름 같은 메타데이터도 온다
- 도구는 채팅 모델을 쓰는 또 다른 방법이다. **특정 입력(payload)이 필요한 API 같은 바깥 도구**에 모델을 연결하고 싶을 때가 있다. 도구를 묶어 두면 모델은 그 함수를 알게 되고, **자연어를 받아 도구를 돌리는 데 필요한 입력을 만들어 낸다**
- 도구가 필요한 질문을 하면 AI 메시지에 content 대신 **tool call** 이 온다. 인자와 도구 이름이 들어 있다
- 메시지를 그래프 State 로 쓴다. 그런데 LangGraph 는 기본적으로 **값을 덮어쓴다**. 대화는 매번 이어 붙여 **전체 기록**을 남겨야 한다 → 이게 **reducer** 가 필요한 이유
- messages 를 이어 붙이는 reducer 는 아주 흔해서, LangGraph 에 **MessagesState** 와 **add_messages** 가 미리 들어 있다
- 그래프: START → 도구를 아는 LLM 노드 → END. "hello" 는 자연어로 답하고, 곱하기를 시키면 tool call 이 나온다

**우리 예로 바꾼 것 / 주의**

- Academy 는 ChatOpenAI 와 `bind_tools`, 곱하기 도구를 쓴다. 우리는 오전의 `chat(messages, tools)` 에 OpenAI 형식 도구 설명을 직접 넘긴다. 하는 일은 같다
- 우리 메시지는 LangChain 메시지 객체가 아니라 오전과 같은 `{ role, content }` 라서, 이어 붙이기 reducer 를 직접 적었다. LangGraph.js 에도 `MessagesAnnotation` 이 있다고 한 줄 언급하면 된다
- 단어 질문은 "사전에서 찾아 줘" 처럼 도구를 쓰라고 분명히 묻는다. 그냥 "무슨 뜻이야?" 라고 하면 모델이 외운 대로 답하기도 한다

## 18장 · Router: 도구냐 답이냐, 모델이 고른다 — 노트북 ②

**말할 것**

방금 그래프는 모델의 판단에 따라 두 가지 중 하나를 했습니다. 도구 요청을 돌려주거나, 바로 답하거나. 이걸 라우터라고 볼 수 있습니다. 모델이 두 길 중 하나를 고르고 있으니까요. 5장에서 말한 가장 작은 Agent 입니다.

이제 두 가지를 더합니다. 하나는 도구를 실제로 실행하는 노드, tools 입니다. 다른 하나는 모델의 답을 보고 길을 고르는 조건부 엣지입니다. 도구 요청이면 tools 로, 아니면 끝으로. tools 가 끝나면 일단 끝으로 가게 해 두겠습니다.

돌려 보면 결론 질문은 tools 를 건너뛰고 바로 끝납니다. 단어 질문은 tools 가 사전을 찾습니다. 그런데 마지막에 남는 건 사전 결과, 날것의 데이터입니다. 학생은 도구 결과를 받고, 모델은 그 결과를 한 번도 보지 못했습니다.

**Academy 에서** (L5)

- 앞 그래프는 메시지를 State 로 쓰고, 도구를 아는 모델이 **도구 호출을 돌려주거나 자연어로 답하거나** 둘 중 하나를 한다. 이건 **간단한 라우터**다. 모델이 두 선택지 사이를 고른다
- 이건 **간단한 Agent** 이기도 하다. LLM 이 애플리케이션의 흐름을 정하고 있다
- 두 가지를 더한다: 도구 호출을 실제로 **실행하는 노드**, 그리고 모델 출력을 보고 **도구 노드로 갈지 끝낼지 고르는 조건부 엣지**
- LangGraph 에는 미리 만든 부품이 있다: **ToolNode** (도구 목록만 넘기면 실행해 준다) 와 **tools_condition** (출력이 tool call 이면 도구 노드로, 아니면 끝으로 가는 조건부 엣지)
- 도구 질문은 도구 노드로 가서 실행되고 tool message 가 나온다. "hello world" 는 도구 노드로 가지 않고 바로 끝난다
- Studio 로 router 를 띄우면 tool call 이 도구 이름과 인자로 보기 좋게 보인다. 이 경우 **사용자는 tool message 를 받는다**

**우리 예로 바꾼 것 / 주의**

- 우리는 ToolNode · toolsCondition 대신 `toolsNode` 와 `route` 를 직접 적었다. 오전 코드와 같은 모양이라 무엇을 하는지 보이게 하려는 것. LangGraph.js 에도 `ToolNode` · `toolsCondition` 이 있다고 언급한다 (LangChain 메시지 형식을 쓸 때 바로 쓸 수 있다)
- Academy 는 "사용자가 tool message 를 받는다" 를 담담하게 말한다. 우리는 이걸 "모델이 결과를 못 봤다" 는 문제로 강조해 다음 장으로 넘긴다

## 19장 · Agent: 선 하나만 바꾼다 — 노트북 ③ · 상한

**말할 것**

라우터를 아주 조금만 고치면, 가장 많이 쓰이는 Agent 구조 중 하나가 됩니다. 라우터에서는 도구를 실행한 결과를 그대로 사용자에게 돌려줬습니다. 그 결과를 사용자 대신 모델에게 다시 보내면 어떨까요? 이게 핵심입니다.

코드에서는 선 하나입니다. tools 에서 END 로 가던 선을, tools 에서 tutor 로 바꿉니다. 아주 작은 수정이지만 의미는 큽니다. 이제 모델이 도구를 부르는 동안 그래프가 계속 돕니다. 모델이 행동하고, 결과를 보고, 그걸 바탕으로 다음을 판단합니다. 오전에 본 ReAct, Thought · Action · Observation 그대로입니다.

단어 두 개를 찾아 쉬운 영어 문장으로 바꿔 달라고 해 보겠습니다. 모델이 두 단어를 찾아 달라고 하고, tools 가 찾고, 결과가 모델에게 돌아가서, 모델이 최종 문장을 만듭니다.

이 루프는 모델이 도구를 부르는 한 계속 돕니다. 그래서 실제로는 다른 조건을 더합니다. LangGraph 는 기본으로 recursionLimit 이라는 상한을 둡니다. 일부러 낮춰서 걸려 보겠습니다. 이건 사고를 막는 안전망이고, 정상적인 멈춤은 실습에서 직접 넣어 봅니다.

**Academy 에서** (L6)

- 라우터를 **한 군데만 고치면** 인기 있는 일반 Agent 구조가 된다. 라우터에서는 tool message 를 사용자에게 돌려줬다. **그걸 모델에게 다시 보내면?** 이게 핵심
- 이게 **ReAct** 구조다. 세 부분: **Act** (모델이 도구를 부른다) · **Observe** (도구 출력을 모델에게 돌려준다) · **Reason** (모델이 그 출력을 보고 다음을 정한다)
- 모델은 문제가 풀렸다고 판단할 때까지 **루프로 도구를 계속 부를 수 있고**, 그러면 자연어로 답하고 끝난다
- 이 루프는 다른 조건을 더하지 않으면 모델이 도구를 부르는 한 계속된다. **실제로는 조건을 더한다. 예를 들어 최대 recursion limit**
- builder 에서 바뀐 건 **tools 노드에서 assistant 로 가는 엣지 하나**뿐이다. 아주 작은 수정인데 큰 의미가 있다
- 예: "3 더하기 4, 거기에 2 곱하기, 그걸 5 로 나누기" → 도구 세 번을 차례로 부르고 2.8 을 답한다
- LangSmith 로 추적(tracing)하면 모델 호출 · 프롬프트 · 도구 호출 · 토큰 · 지연 시간을 단계별로 볼 수 있다. Studio 와 짝을 이루는 도구다
