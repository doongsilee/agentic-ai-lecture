## 3장 · 개발 프로젝트 ① LaunchBound

**말할 것**

첫 번째는 LaunchBound 입니다. 개발팀을 위한 매니지먼트 Agent 입니다.

개발팀은 하루 종일 여러 도구를 오갑니다. 대화는 Slack 에, 코드는 GitHub 에, 디자인은 Figma 에, 일감은 Jira 에 있습니다. 정보가 이렇게 흩어져 있으니 "이 기능 어디까지 됐어?", "이 디자인 바뀐 거 문서에 반영됐어?" 같은 질문에 답하려면 사람이 여기저기 뒤져야 합니다.

LaunchBound 는 이 도구들에서 정보를 모아 한곳에서 봅니다. 그리고 팀원의 요청에 답하고, 관련 자료를 찾아 주고, 코드나 결정이 바뀌면 관련 문서를 자동으로 고치고, 업무 관리를 돕습니다.

오른쪽의 하는 일을 보시면 코드 수정, 문서 업데이트, Slack 메시지, 챗으로 답하기입니다. 답만 하는 게 아니라 실제로 바깥 세상을 바꾸는 행동을 합니다. 오늘 오전에 배울 말로 하면 이게 전부 도구입니다. 가운데 두뇌와 하네스라는 말은 잠시 뒤에 자세히 설명드리겠습니다.

**주의**

- 이 장과 다음 두 장은 신뢰를 주려는 장이다. 기능을 길게 설명하지 말고 장당 1분 안팎으로
- 하는 일 중 코드 수정 · 문서 업데이트는 되돌리기 어려운 행동이다. 질문이 오면 "그래서 사람 승인이 중요하다, 오후에 다룬다" 로 넘긴다

## 4장 · 개발 프로젝트 ② Practly

**말할 것**

두 번째는 Practly 입니다. 영어 시험을 준비하는 학습자를 위한 튜터 Agent 입니다.

학습자가 말하기 스크립트나 쓰기 답안의 초안을 넣으면, Practly 는 바로 대화를 시작하지 않습니다. 먼저 초안을 분석해서 무엇을 가르칠지 고릅니다. 이게 ① 사전 분석입니다.

그다음 ② 튜터 단계에서는 답을 바로 알려 주지 않고 소크라틱하게 질문합니다. "이 문장에서 시제가 맞을까요?" 처럼 물어서 학습자가 스스로 고치게 합니다. 그리고 학습자의 답을 보고 다음 질문을 고릅니다. 잘 이해했으면 넘어가고, 헷갈려하면 다르게 다시 묻습니다. 같은 걸 가르쳐도 학습자마다 길이 달라지게 설계했습니다.

행동은 질문하기, 그리고 화면에 고칠 곳 밑줄을 긋거나 기억할 내용을 자동으로 추려서 보여 주는 것입니다. 글로만 답하는 게 아니라 화면을 직접 움직입니다.

단순한 대화 챗봇이었다면 학습자가 묻는 말에 답만 했을 겁니다. Agent 이기 때문에 먼저 보고, 묻고, 답을 보고 다음을 정합니다.

참고로 오후에 LangGraph 예제로 쓰는 영어 튜터가 이 프로젝트를 아주 작게 줄인 것입니다.

**주의**

- 소크라틱 질문 = 답을 주지 않고 질문으로 스스로 찾게 하는 방식. 처음 듣는 분이 있으면 한 줄로 풀어 준다

## 5장 · 개발 프로젝트 ③ Livehero

**말할 것**

마지막은 Livehero 입니다. 라이브 방송을 하는 크리에이터를 위한 AI 매니저입니다.

라이브 방송에서는 두 가지가 끊임없이 들어옵니다. 시청자 채팅, 그리고 크리에이터가 하는 말입니다. Livehero 는 크리에이터의 말을 STT, 그러니까 음성 인식으로 글로 바꾸고 채팅과 함께 실시간으로 받습니다.

그걸 바탕으로 다섯 가지를 합니다. 누가 주요 팬인지 분석하고, 중요한 채팅을 골라내고, 그 결과를 방송 화면에 오버레이로 바로 띄웁니다. 진행자가 다음에 할 말을 대본으로 써 주고, 위험한 발언이 나오면 잡아냅니다.

앞의 두 개와 다른 점은 멈추지 않는다는 겁니다. 질문 하나에 답하고 끝나는 게 아니라 방송 내내 들어오는 것을 보고 계속 할 일을 고릅니다.

세 Agent 는 하는 일이 전혀 다르지만 구조는 같습니다. 바깥에서 정보를 받고, LLM 이 판단하고, 도구로 행동합니다. 오늘 오전에 이 공통 구조를 직접 만들어 보겠습니다.

**주의**

- 위험 발언 분석은 사람이 최종 판단한다는 걸 덧붙여도 좋다 (오후 ③ 사람 승인과 이어진다)

## 6장 · 오늘 과정의 목적

**말할 것**

오늘 과정의 목적부터 말씀드리겠습니다. 오늘은 LLM 자체를 다루지 않습니다. 모델을 어떻게 학습시키는지, 구조가 어떤지는 거의 안 봅니다. 대신 LLM 을 가져다가 실제로 일을 하는 프로그램, AI Agent 를 어플리케이션 레벨에서 어떻게 만드는지를 봅니다.

목표는 두 가지입니다. 오전에는 Agent 가 무엇인지 압니다. Agent, LLM, Tool 이라는 세 개념을 잡고, 프레임워크 없이 첫 Agent 를 직접 만들어 봅니다. 오후에는 LangGraph 의 기초를 익힙니다. 오전에 만든 루프를 그래프로 옮기고, State, 사람 승인, 메모리까지 다룹니다.

이 강의는 여러분이 개발 경험이 있고 코드를 읽고 고칠 수 있다고 가정합니다. TypeScript 는 처음이셔도 괜찮습니다. 오늘 쓰는 문법은 함수, 배열, 반복문 정도입니다.

그리고 딥러닝을 연구하시는 분들도 계신 걸로 압니다. 모델 내부는 여러분이 저보다 더 잘 아실 수도 있습니다. 오늘은 그 반대쪽, 모델 바깥에서 모델을 감싸고 움직이는 코드를 보겠습니다.

**주의**

- "TypeScript 처음이어도 괜찮다" 는 진심으로 말한다. 실습 코드는 정답이 장표에 다 있고, 막히면 `pnpm step` 이 있다

## 8장 · AI Agent 란 무엇인가?

**말할 것**

본론으로 들어가겠습니다. AI Agent 가 무엇인지, 질문 하나로 시작해 보겠습니다.

"2026년 10월 29일, 그러니까 오늘이죠. 제2교육장에서 2시간짜리 교육을 잡을 수 있어?"

이 질문을 그냥 LLM 에게 하면 어떻게 될까요. 두 가지 중 하나입니다. "죄송하지만 예약 현황은 확인할 수 없습니다" 하고 모른다고 하거나, "오후 2시에서 4시가 비어 있을 가능성이 높습니다" 하고 그럴듯하게 지어냅니다. 어느 쪽이든 모델은 실제 예약 현황을 하나도 보지 않았습니다.

같은 질문을 Agent 에게 하면 다릅니다. 먼저 예약 일정을 조회합니다. 오전에는 정비교육이 있고 13시에는 안전교육이 있다는 걸 봅니다. 그걸 보고 "그럼 장비 점검 일정도 봐야겠다" 하고 다시 조회합니다. 15시에 프로젝터 점검이 있습니다. 그리고 남는 2시간을 계산해서 "16시부터 18시가 비어 있습니다" 라고 답합니다.

차이는 두 가지입니다. 직접 확인했다는 것, 그리고 확인한 결과를 보고 다음 할 일을 스스로 정했다는 것입니다. 점검 일정을 보자는 건 처음부터 정해진 게 아니었습니다. 첫 조회 결과를 보고 나서 정했습니다. 오늘 오전 내내 이 차이를 코드로 만들어 볼 겁니다.

## 9장 · Agent 는 무엇인가?

**말할 것**

그럼 Agent 를 조금 더 정확하게 정의해 보겠습니다.

Agent 는 목표를 받아서, 환경을 보고, 행동을 고르고, 그 결과를 보고 다시 고르는 시스템입니다. 그림으로 보면 "29일에 교육 2시간 잡아 줘" 라는 목표가 Agent 에게 들어갑니다. Agent 안에는 판단하고 계획하는 두뇌가 있고, 도구와 기억과 상한을 가진 몸이 있습니다. 몸이 환경, 그러니까 일정 DB 나 점검 기록이나 사람에게 행동을 하고, 그 결과를 관찰해서 다시 두뇌에게 보여 줍니다.

이 정의는 새로운 게 아닙니다. 고전 AI 교과서인 Russell 과 Norvig 의 책에서도 Agent 를 "센서로 환경을 인식하고, 행동으로 환경에 작용하는 것" 이라고 정의합니다. 로봇 청소기도, 자율주행차도 이 정의에 들어갑니다.

달라진 건 하나입니다. 무엇을 할지 "고르는" 자리에 예전에는 사람이 만든 규칙이 들어갔는데, 지금은 LLM 이 들어갔습니다. 규칙으로 다 적을 수 없던 상황도 LLM 은 글을 읽고 판단할 수 있습니다.

그리고 가장 중요한 건 마지막 줄입니다. 한 번 답하고 끝나지 않습니다. 결과를 보고 다음을 정합니다. 이게 Agent 의 핵심입니다.

**주의**

- "Agent" 는 업계에서 아주 넓게 쓰인다. 정해진 순서로 LLM 을 부르는 것도 Agent 라고 부르는 사람이 있다. 오늘은 "결과를 보고 다음을 정한다" 를 기준으로 삼는다고만 말한다 (오후 ① 에서 체인 · 라우터 · Agent 로 다시 나눈다)
- 출처 줄(Russell & Norvig, HF Agents Course Unit 1)은 읽지 않아도 된다

## 10장 · 두뇌는 LLM, 몸은 Harness

**말할 것**

방금 그림에서 Agent 를 두뇌와 몸으로 나눴습니다. 오늘 하루 계속 쓸 말이니 조금 더 보겠습니다.

두뇌는 LLM 입니다. 상황을 판단하고, 계획을 세우고, 다음 행동을 고르고, 말을 합니다. 두뇌가 "다음에 이걸 하자" 하고 내보내면, 몸이 그걸 실행하고 결과를 다시 두뇌에게 돌려줍니다.

몸에는 네 가지가 있습니다. 손은 도구입니다. 실제로 조회하고, 바꾸고, 보냅니다. 눈은 관찰입니다. 실행 결과를 받아서 두뇌에게 다시 보여 줍니다. 기억은 State 입니다. 지금까지 무엇을 했는지, 지난번에 무엇을 했는지 들고 있습니다. 마지막으로 안전장치가 있습니다. 끝없이 돌거나 위험한 일을 하려고 할 때 멈춰 세웁니다. 몇 번까지만 돌게 하는 횟수 상한이나, 사람에게 승인받기 같은 것입니다.

이 몸을 Harness 라고 부릅니다. 원래 뜻은 말에 채우는 마구입니다. 고삐나 굴레처럼, 힘센 말이 원하는 방향으로 일하게 만드는 장비죠. AI 에서도 똑같습니다. 힘센 모델을 감싸서 실제로 일하게 만드는 모든 것이 하네스입니다. 도구를 쥐여 주고, 결과를 보여 주고, 기억을 이어 주고, 필요하면 멈춰 세웁니다.

두뇌만 있으면 말만 잘합니다. 몸이 있어야 일을 합니다. 그래서 하네스는 두뇌를 뺀 나머지 전부라고 보시면 됩니다.

그리고 같은 두뇌라도 몸에 따라 결과가 크게 갈립니다. 같은 모델을 써도 어떤 제품은 일을 잘하고 어떤 제품은 못합니다. 그 차이는 대부분 하네스에서 납니다. 오늘 우리가 직접 구현하는 것도 바로 이 하네스입니다.

**주의**

- "하네스" 는 영어 그대로 쓴다. 한국어로 옮기지 않는다
- 질문: "그럼 프레임워크가 하네스냐?" → 프레임워크는 하네스를 만드는 재료다. 하네스는 우리가 만든 결과물 전체

## 11장 · ChatGPT 이후, 우리가 모델에 붙여 온 것들

**말할 것**

지난 몇 년을 이 두뇌와 몸으로 다시 보면 흐름이 보입니다.

2022년 11월에 ChatGPT 가 나왔습니다. 대화로 쓰는 LLM 의 시작이었고, 이때는 두뇌만 있었습니다.

2023년에는 프롬프트 엔지니어링이 유행했습니다. 잘 물어보면 더 잘한다는 것, 두뇌에게 지시를 잘 주는 법이었습니다. 같은 해에 RAG 가 나왔습니다. 모델이 모르는 자료는 찾아서 넣어 주자는 것, 기억과 지식을 붙인 겁니다. 그리고 2023년 6월에 Tool Calling 이 나왔습니다. 모델이 말 대신 행동을 요청할 수 있게 됐습니다. 손이 생긴 거죠.

2024년 11월에는 MCP 가 나왔습니다. 도구를 꽂는 표준 규격입니다. USB-C 처럼, 손을 꽂는 소켓을 통일한 겁니다. 2025년에는 Context Engineering 이라는 말이 퍼졌습니다. 매번 모델에게 무엇을 보여 줄지 고르는 일, 눈과 기억을 관리하는 일입니다. 그리고 올해, 2026년에는 이 모든 걸 묶어서 루프를 돌리고, 멈추고, 승인받는 Agent 하네스, 몸 전체가 이야기의 중심이 됐습니다.

모델도 물론 좋아졌습니다. 그런데 모델이 실제로 일을 하게 만든 건 대부분 모델 바깥이었습니다.

**주의**

- 연도는 대략이다. "정확히 그해에 처음 나왔다" 보다 "그 무렵 널리 쓰이기 시작했다" 로 말한다
- RAG 논문 자체는 2020년이다. 질문이 오면 "널리 쓰인 건 2023년 무렵" 으로

## 12장 · Agent 는 무슨 일을 할 수 있나?

**말할 것**

그럼 지금 Agent 들은 실제로 무슨 일을 하고 있을까요. 몇 가지 분야로 나눠 보겠습니다. 이름을 다 기억하실 필요는 없고, 각 Agent 가 어떤 도구를 쥐고 있는지만 보시면 됩니다.

일반 업무 Agent 는 자료를 찾아 읽고, 파일과 메일과 문서를 오가며 사무 일을 끝까지 처리합니다. Claude Cowork, Copilot Cowork, ChatGPT agent 같은 것들입니다. 쥐고 있는 도구는 폴더 속 파일을 읽는 도구, 메일과 문서에 연결하는 커넥터입니다.

코딩 Agent 는 코드를 읽고 고친 뒤 테스트를 돌려 스스로 확인합니다. Claude Code, Codex, Cursor 입니다. 도구는 파일 고치기, 터미널 명령 실행입니다. 테스트가 실패하면 그 결과를 보고 다시 고칩니다. 아까 말한 "결과를 보고 다음을 정한다" 가 그대로 있습니다.

개인비서 Agent 는 메신저로 일을 맡기면 메일, 일정, 결제까지 대신합니다. 웹 브라우저를 대신 조작하는 도구, 메신저로 보고하는 도구를 씁니다.

보안 Agent 는 취약점 후보를 찾고, 실제로 뚫리는지 직접 공격을 재현해서 확인합니다. XBOW 나 구글의 Big Sleep 같은 것들입니다.

그리고 산업마다 특화된 Agent 들이 빠르게 생기고 있습니다. 고객 응대, 법률, 의료, 금융, 영업, 채용, 음성 전화, IT 운영, 그리고 국방도 있습니다.

보시면 분야마다 두뇌는 비슷한 LLM 을 씁니다. 다른 건 손, 그러니까 어떤 도구를 쥐여 줬느냐입니다.

**주의**

- 시간이 모자라면 이 장을 가장 먼저 줄인다. "도구가 다르다" 한 문장만 남겨도 된다
- 특정 제품을 추천하거나 비교하지 않는다

## 13장 · LLM 은 다음 말을 예측하는 도구에 불과하다

**말할 것**

이제 두뇌, LLM 을 보겠습니다. 결론부터 말하면 LLM 은 다음 말을 예측하는 도구입니다.

"서울의 오늘 날씨는" 까지 넣으면, 모델은 다음에 올 토큰 후보들에 확률을 매깁니다. "맑" 이 41%, "흐" 가 23%, "비" 가 12% 같은 식입니다. 그중 하나를 고릅니다. 고른 토큰을 뒤에 붙여서 다시 넣습니다. "서울의 오늘 날씨는 맑" 을 넣으면 "음" 이 나오고, 다시 넣으면 마침표가 나옵니다. 이렇게 한 토큰씩 이어 써서 "서울의 오늘 날씨는 맑음." 이 됩니다.

가운데 Transformer 내부는 오늘 생략합니다. 오늘 중요한 건 맨 아래 한 줄입니다. 모델은 이 문장을 쓰면서 실제 날씨를 한 번도 보지 않았습니다. 그럴듯한 다음 말을 골랐을 뿐입니다.

**주의**

- 딥러닝 연구자에게는 너무 쉬운 장이다. "아시는 분들께는 복습입니다" 하고 빨리 넘긴다
- 확률 숫자는 예시다

## 14장 · 그런데 이 단순한 모델이 어떻게 이렇게 똑똑해졌을까?

**말할 것**

그런데 다음 말 예측기가 어떻게 도구를 부르고 계획까지 세우게 됐을까요. 같은 질문, "29일에 제2교육장 비어 있어?" 로 학습 단계를 따라가 보겠습니다.

첫 단계는 사전학습입니다. 인터넷에서 가져온 방대한 글로 다음 말 예측을 학습합니다. 이 단계의 모델에게 같은 질문을 넣으면 답을 하지 않습니다. "30일에 제3교육장은 어때? 31일에는…" 하고 비슷한 질문을 이어 씁니다. 인터넷에 그런 글 목록이 많으니까요. 이 단계에서 생기는 건 글을 이어 쓰는 능력과 세상 지식입니다.

두 번째는 지시 학습, SFT 입니다. 질문과 좋은 답의 예시를 보여 줍니다. 그러면 "29일 제2교육장은 오후에 비어 있을 가능성이 높습니다. 예약을 도와드릴까요?" 처럼 대화하는 모양으로 답합니다. 대화하는 방식과 지시를 따르는 법이 생깁니다. 다만 보시면 여전히 확인은 안 하고 그럴듯하게 답합니다.

세 번째는 강화 학습, RL 입니다. 결과가 좋은 쪽에 보상을 줍니다. 사람이 더 좋다고 고른 답일 수도 있고, 수학이나 코드처럼 정답을 확인할 수 있는 문제일 수도 있습니다. 이 단계를 거친 모델은 "일정부터 봐야 한다" 하고 생각한 뒤 get_schedule 을 부르고, 결과를 보고 "잠깐, 장비 점검도 봐야 한다" 하며 get_maintenance 를 부릅니다. 생각하는 능력과 도구 호출 능력이 생깁니다.

여기서 기억하실 건 맨 아래 한 줄입니다. 도구를 부르는 것도, 오래 생각하는 것도 모델이 학습으로 익힌 습관입니다. 모델 안에 도구 실행기가 들어 있는 게 아닙니다.

**주의**

- 실제 학습 과정은 이보다 복잡하다 (선호 학습의 여러 방식, 단계 반복 등). 연구자가 짚으면 "세 단계로 단순화했다" 고 인정한다
- get_schedule · get_maintenance 는 예시 이름이다

## 15장 · 그래도 바뀌지 않은 것: 여전히 다음 말 예측기다

**말할 것**

그렇게 똑똑해졌어도 바뀌지 않은 게 있습니다. 여전히 다음 말 예측기라는 겁니다. 그래서 생기는 성질 네 가지를 보겠습니다.

첫째, 지난 대화를 기억하지 못합니다. 매번 앞 내용을 전부 다시 받습니다. 그래서 대화라는 건 사실 한 줄의 긴 글입니다.

둘째, 글자가 아니라 토큰으로 셉니다. 비용도, 속도도, 길이 한도도 전부 토큰입니다.

셋째, 한 번에 볼 수 있는 양이 정해져 있습니다. 이걸 컨텍스트 윈도우라고 합니다. 길어질수록 느려지고, 중간 내용을 놓칩니다.

넷째, 오늘 일도, 우리 자료도 모릅니다. 학습이 끝난 뒤의 일과 우리 내부 자료는 본 적이 없습니다. 그래서 도구가 필요합니다.

이것들을 다루는 게 하네스의 일입니다. 다음 장부터 앞의 세 개를 하나씩 보고, 네 번째인 도구는 그 뒤에 따로 보겠습니다.

## 16장 · "대화" 는 사실 한 줄의 긴 글이다

**말할 것**

첫 번째, 대화는 한 줄의 긴 글이라는 얘기입니다.

우리가 채팅 화면에서 보는 건 위쪽 모습입니다. "29일에 제2교육장 비어 있어?" 하고 물으면 "16시 이후가 비어 있습니다" 하고 답하고, 다시 "그럼 그 시간으로 잡아 줘" 라고 묻습니다.

그런데 두 번째 질문을 보낼 때 모델이 실제로 받는 건 아래쪽입니다. 맨 앞에 "너는 교육장 일정 담당이다" 라는 system 메시지가 있고, 첫 질문, 첫 답, 그리고 새 질문이 차례로 들어 있습니다. 이미 한 대화도 매번 통째로 다시 보냅니다. 그리고 맨 끝 assistant 자리부터 모델이 이어 씁니다.

모델 눈에는 처음부터 끝까지 이어진 글 한 덩어리입니다. 아까 본 "다음 말 예측" 을 이 긴 글 끝에서 하는 거죠. 그래서 대화가 길어질수록 보내는 글이 길어지고, 느려지고, 비싸집니다.

여기서 role 이 세 가지 나왔습니다. system 은 개발자가 정하는 역할과 규칙, user 는 사용자가 한 말, assistant 는 모델이 한 말입니다. 실습 1 에서 이걸 직접 만듭니다.

**주의**

- "ChatGPT 는 기억하던데요?" → 기억 기능도 하네스가 지난 내용을 찾아서 messages 에 넣어 주는 것이다. 모델이 기억하는 게 아니다

---

## 17장 · 이 글의 양은 글자 수가 아니라 토큰으로 잰다

**말할 것**

두 번째, 그 긴 글의 양은 토큰으로 잽니다.

방금 그 질문을 토크나이저로 잘라 보면 이렇습니다. "29일에 제2교육장 비어 있어?" 는 글자로 17자, 토큰으로는 11개입니다. 같은 뜻의 영어 문장 "Is training room 2 free on the 29th?" 는 글자로 36자인데 토큰은 12개입니다. 글자 수는 두 배 차이인데 토큰 수는 거의 같습니다.

토큰은 모델이 글을 자르는 단위입니다. 자주 나오는 덩어리는 한 토큰이 되고, 드문 건 잘게 쪼개집니다. 비용, 속도, 길이 한도를 전부 이 토큰으로 셉니다. API 요금표를 보시면 "백만 토큰당 얼마" 로 나와 있습니다.

그리고 자르는 방법은 토크나이저마다 다릅니다. 같은 한국어 문장이 예전 GPT-4 토크나이저로는 15 토큰이었습니다. 최신 토크나이저로 오면서 한국어를 더 효율적으로 자르게 된 겁니다. 같은 글이어도 모델에 따라 비용이 달라질 수 있다는 뜻입니다.

궁금하시면 OpenAI 토크나이저 페이지에서 직접 넣어 보실 수 있습니다.

**주의**

- 숫자는 GPT-4o 토크나이저(o200k) 기준이다. 실습 모델(qwen3-32b)은 토크나이저가 달라 숫자가 다르다

## 18장 · 컨텍스트 윈도우: 한 번에 넣을 수 있는 토큰의 최대치

**말할 것**

세 번째, 컨텍스트 윈도우입니다. 모델이 한 번에 받을 수 있는 토큰의 최대치입니다. 요즘 모델은 수십만에서 백만 토큰까지 됩니다.

그림을 보시면 질문할 때마다 막대가 길어집니다. 매번 system, 지난 질문과 답, 새 질문을 다 보내니까요. 그러다 N 번째 질문쯤 되면 한도를 넘습니다.

한도를 넘으면 두 가지 중 하나가 일어납니다. 에러가 나거나, 앞부분이 잘려 나갑니다. 어느 쪽인지는 서버마다 다릅니다.

그리고 한도 안이어도 문제가 있습니다. 길어질수록 느려지고, 비싸지고, 중간 내용을 놓치기 쉽습니다. 백만 토큰이 들어간다고 백만 토큰을 다 꼼꼼히 보는 건 아닙니다.

그래서 무엇을 남기고 무엇을 뺄지 정하는 게 하네스의 일입니다. 앞에서 Context Engineering 이라고 한 게 바로 이 일입니다.

**주의**

- "중간을 놓친다" 는 lost in the middle 현상. 질문이 오면 이름만 알려 준다

## 19장 · 시연: LLM 을 직접 불러 보자

**말할 것**

지금까지 본 걸 실제로 확인해 보겠습니다. LLM 을 직접 불러 보겠습니다. 오늘은 Jupyter 노트북에서 TypeScript 로 돌립니다.

네 가지를 봅니다. 첫째, LLM 호출은 HTTP 요청 하나라는 것. 둘째, 대화는 긴 messages 배열이라는 것. 셋째, 질문할 때마다 토큰이 쌓인다는 것. 넷째, 한도를 넘기면 잘린다는 것입니다.

**시연 순서** (`demo/llm-call.ipynb`)

1. 첫 셀: 접속 정보 세 줄. "이 세 값만 바꾸면 OpenAI 든 Ollama 든 같은 코드로 돈다" 를 짚는다. 기본값은 이 PC 의 로컬 Ollama
2. ① fetch 한 번: `/chat/completions` 에 POST, body 에 model 과 messages. 응답 전체를 찍어서 `choices[0].message` 가 `{ role: "assistant", content }` 메시지 하나라는 것, `usage` 에 토큰 수가 있다는 것을 보여 준다. "실습 1 에서 이걸 직접 합니다"
3. ② 같은 질문 뒤에 "방금 추천한 시간을 다시 말해 줘"
   - 답을 배열에 넣지 않으면: 모른다고 하거나 다른 시간을 지어낸다
   - 답을 assistant 메시지로 넣으면: 제대로 말한다
   - 말할 것: "모델이 기억한 게 아닙니다. 제가 배열에 넣어서 다시 보낸 만큼만 압니다"
4. ③ 질문을 여러 번 이어 가며 입력 토큰이 계속 느는 것을 본다
5. ④ 암호 시험: 맨 앞에 "암호는 '파란 고래'" 를 숨기고 메모로 글을 늘린다
   - 메모 100번: 기억한다
   - 메모 400번: 약 4,900 토큰을 보냈는데 실제로 들어간 건 2,000 토큰 남짓. 오류 없이 조용히 잘려서 암호가 사라졌다
   - 말할 것: "Ollama 는 이렇게 조용히 자르고, OpenAI 는 에러를 냅니다. 어느 쪽이든 무엇을 남길지는 하네스가 정해야 합니다"

**주의**

- 로컬 Ollama 가 떠 있는지 강의 전에 확인한다. ④ 는 컨텍스트 4,096 으로 띄운 Ollama 에서만 잘리는 모습이 나온다
- 모델 답은 매번 달라진다. ② 의 "답을 안 넣었을 때" 가 우연히 맞히면 "운 좋게 같은 시간을 다시 골랐을 뿐" 이라고 말하고 한 번 더 돌린다

---

## 20장 · 도구란 무엇인가?

**말할 것**

이제 네 번째, 도구입니다.

LLM 은 답을 만들어 낼 뿐, 바깥 세상에 손을 댈 수 없습니다. 그 손이 되어 주는 함수가 도구입니다. 도구는 거창한 게 아니라 우리가 만든 평범한 함수입니다.

도구가 하는 일을 다섯 가지로 나눠 보겠습니다.

찾아오기. 모르는 것, 최신 정보를 가져옵니다. 웹 검색, 사내 문서 검색, DB 나 일정 조회가 여기 들어갑니다.

보여 주기. 글 말고 다른 모양으로 전합니다. 차트나 표를 그리거나, 화면에 밑줄을 긋거나, 소리로 읽어 줍니다.

계산과 실행. 정확해야 하는 일은 코드에게 맡깁니다. 다음 말 예측기에게 큰 수 곱셈을 시키면 틀릴 수 있습니다. 계산기를 쥐여 주면 됩니다.

바꾸기와 보내기. 바깥 세상에 흔적을 남깁니다. 파일 수정, 메일 보내기, 일정 등록, 결제. 이 도구들은 되돌리기 어렵습니다. 그래서 조심해야 합니다.

묻기와 맡기기. 혼자 정하지 않고 넘깁니다. 사람에게 확인받거나 다른 Agent 에게 맡기는 것도 도구로 만들 수 있습니다.

**주의**

- "바꾸기 · 보내기" 의 위험이 오후 ③ 의 사람 승인으로 이어진다. 여기서는 "조심해야 한다" 까지만

---

## 21장 · LLM 은 실제로 도구를 실행하지 않는다

**말할 것**

오늘 오전에서 가장 중요한 장입니다. LLM 은 실제로 도구를 실행하지 않습니다.

도구 호출은 세 단계로 일어납니다.

첫째, 프롬프트에서 LLM 에게 도구를 알려 줍니다. 어떤 도구가 있고, 언제 쓰고, 어떻게 부르는지. 예를 들어 이름은 get_schedule, 언제 쓰냐면 교육장 일정을 알아야 할 때, 어떻게 부르냐면 장소와 날짜를 넣어서.

둘째, LLM 이 도구를 호출합니다. 어떤 도구를 어떤 값으로 부를지 고릅니다. "get_schedule 을 제2교육장, 10월 29일로" 처럼요. 그런데 여기서 LLM 이 하는 건 그 요청을 글로 쓰는 것뿐입니다. 실행은 하지 않습니다.

셋째, 실행은 우리 책임입니다. 우리 코드가 그 요청을 읽어서 실제로 함수를 실행합니다. 그리고 실행을 통제하는 것도 우리 몫입니다. 이 요청이 권한이 있는 요청인가, 위험하면 사람에게 승인받아야 하는가. DB 나 파일이나 네트워크에 연결하는 환경도 우리가 깔아 줘야 하고, 실패하면 어떻게 할지도 정해야 합니다. 결과를 LLM 에게 돌려줄지, 사용자에게 바로 보여 줄지도 우리가 정합니다.

정리하면 LLM 이 하는 일은 두 번째, 호출할 도구를 고르는 것 하나입니다. 나머지는 전부 하네스의 몫입니다.

**주의**

- 질문: "그럼 ChatGPT 의 웹 검색은?" → 그것도 OpenAI 쪽 하네스가 실행한다. 모델은 고를 뿐
- 이 장을 이해하면 실습 3 · 4 가 쉽다. "실습 3 에서 ② 까지 보고, 실습 4 에서 여러분이 세 번째 단계를 직접 구현합니다" 로 이어 준다

---

## 22장 · MCP: 도구를 꽂는 표준 규격

**말할 것**

앞에서 MCP 를 USB-C 같은 것이라고 했습니다. 왜 필요한지 보겠습니다.

하네스가 세 개 있다고 해 봅시다. Claude Code, Cursor, ChatGPT. 그리고 연결하고 싶은 도구가 네 개 있습니다. 파일, 사내 DB, 메신저, 일정과 메일. MCP 가 없으면 하네스마다 도구마다 따로 연동을 만들어야 합니다. 3 곱하기 4, 12번입니다.

MCP 가 있으면 도구는 MCP 규격에 맞춰 한 번만 만들고, 하네스도 MCP 를 한 번만 지원하면 됩니다. 3 더하기 4, 7번입니다. 하네스와 도구가 늘어날수록 차이는 커집니다.

규격이 정하는 건 크게 두 가지입니다. 하나는 도구 목록 묻기. "무슨 도구가 있어?" 하고 물으면 이름, 언제 쓰는지, 넣을 값을 돌려줍니다. 아까 본 도구 설명 세 가지 그대로입니다. 다른 하나는 실행 요청하기. "이 값으로 실행해 줘" 하면 서버가 실행하고 결과를 돌려줍니다.

그리고 MCP 가 바꾸지 않는 게 있습니다. 도구를 고르는 건 여전히 LLM 이고, 승인하고 결과를 처리하는 건 여전히 하네스입니다. MCP 는 소켓을 통일했을 뿐, 누가 무엇을 하는지는 그대로입니다.

**주의**

- 시간이 모자라면 12장 다음으로 줄인다. 3 × 4 와 3 + 4 만 보여 줘도 된다
- 오늘 실습에서는 MCP 를 쓰지 않는다. 질문이 오면 "도구를 함수로 직접 붙이는 것과 원리가 같다" 고 답한다

## 23장 · 시연: 도구를 직접 불러 보자

**말할 것**

도구를 직접 불러 보겠습니다. 두 가지를 봅니다. 도구를 알려 주면 LLM 은 답 대신 요청만 돌려준다는 것, 그리고 실행은 우리 코드에서 한다는 것입니다.

**시연 순서** (`demo/tool-call.ipynb` ① ~ ③)

1. ① `tools` 에 get_schedule 을 적는다. name · description · parameters 가 21장의 이름 · 언제 · 어떻게 그대로라는 것을 짚는다
2. "29일에 제2교육장 비어 있어?" 를 보낸다
   - `content` 는 비어 있고 `tool_calls` 에 도구 이름과 값이 있다
   - `finish_reason: "tool_calls"`: 답이 아니라 도구 요청이라는 뜻
   - `arguments` 는 JSON 문자열이다. "LLM 은 글을 썼을 뿐입니다"
3. "교육장 예약은 보통 며칠 전에 하는 게 좋아?" 를 같은 도구와 함께 보낸다 → 도구를 부르지 않고 바로 답한다. "부를지 말지도 LLM 이 고릅니다"
4. ② 예약 장부를 흉내 낸 평범한 함수 getSchedule 을 보여 준다. 요청을 읽어 우리가 실행하고, 결과를 `role: "tool"` 메시지로, `tool_call_id` 로 짝을 맞춰 넣는다. 다시 부르면 결과를 보고 답한다. "LLM 은 두 번 불렸습니다. 한 번은 고르려고, 한 번은 결과를 보고 답하려고. 그 사이에서 실행한 건 우리 코드입니다"
5. ③ 실행하지 않고 결과를 지어내서 넣는다 ("공사로 사용 불가") → 모델이 그대로 믿고 답한다. "모델은 messages 에 적힌 대로 믿습니다. 진짜 결과를 넣는 건 하네스의 책임입니다"

**주의**

- ③ 은 장표에 카드가 없지만 꼭 보여 준다. 하네스 책임을 가장 잘 보여 주는 장면이다

## 24장 · 도구를 실행한 다음엔?

**말할 것**

도구를 실행하고 나면 결과가 생깁니다. 그 결과로 무엇을 할까요. 두 갈래가 있습니다.

첫째, 다시 LLM 에게 보냅니다. 결과를 messages 에 넣고 다시 부릅니다. 방금 시연에서 본 기본 흐름입니다. LLM 이 결과를 보고 다음 판단을 합니다.

둘째, 여기서 끝냅니다. 결과를 화면에 바로 띄우거나, 최종 제출을 하거나, 사람에게 넘깁니다. LLM 에게 다시 보내지 않습니다. 예를 들어 표를 그리는 도구라면 그 표를 사용자에게 바로 보여 주면 되지, 모델에게 다시 보여 줄 필요는 없습니다.

어느 쪽으로 갈지는 하네스가 정합니다. 그리고 첫 번째 갈래가 반복되면, 그게 루프가 됩니다.

---

## 25장 · Thought → Action → Observation

**말할 것**

그 루프를 그림으로 그리면 이렇습니다. Thought, Action, Observation 의 반복입니다.

Thought 는 다음에 뭘 할지 판단하는 단계입니다. 모델이 합니다. Action 은 도구 요청, 아까 본 tool_calls 입니다. 요청을 쓰는 건 모델이고, 실행하는 건 하네스입니다. Observation 은 실행 결과, role tool 메시지입니다. 하네스가 messages 에 넣습니다. 그리고 결과를 보고 다시 Thought 로 돌아갑니다. 충분하다고 판단하면 루프를 빠져나와 최종 답을 냅니다.

이 구조를 ReAct 라고 부릅니다. Reason 과 Act 를 합친 말입니다. 원래는 모델에게 판단을 글로 먼저 쓰게 하면 다음 행동을 더 잘 고른다는 아이디어였습니다. 지금 모델들은 이 사이클을 학습해서, 따로 시키지 않아도 tool_calls 로 바로 냅니다. 14장에서 본 강화 학습이 이 습관을 만든 겁니다.

Thought 는 요즘 모델의 생각 단계로 볼 수 있습니다. 요즘 모델은 답하기 전에 따로 생각합니다. 다음 시연에서 바퀴마다 찍히는 Thought 가 바로 그 생각입니다.

그리고 하나 더. 에러도 Observation 입니다. 도구가 실패하면 프로그램을 멈추지 말고 "실패: 응답 없음" 같은 결과를 돌려줍니다. 그러면 모델이 그걸 보고 다른 길을 찾습니다. 실습 5 · 6 에서 이걸 직접 보게 됩니다.

**주의**

- ReAct 논문은 2022년 (Yao 외). 질문이 오면 이름만 알려 준다

---

## 26장 · 시연: 루프로 감싸 보자

**말할 것**

이제 한 바퀴를 루프로 감싸 보겠습니다. 세 가지를 봅니다. 결과를 보고 다음 도구를 고르는 것, 모델이 스스로 끝내는 것, 그리고 하네스가 끊는 것입니다.

그리고 미리 말씀드리면, 루프는 모델 안에 있는 게 아니라 우리 코드의 while 문입니다.

**시연 순서** (`demo/tool-call.ipynb` ④)

1. 도구 두 개: find_free_rooms(날짜) 와 점검 일정 조회. "두 번째 도구는 첫 번째 결과를 봐야 부를 수 있습니다. 어느 교육장을 조회할지 처음에는 모르니까요"
2. runAgent 코드를 보여 준다. for 문 안에서 부르고, tool_calls 가 없으면 break, 한도를 넘으면 break. 끝나는 길 두 개를 짚는다
3. 끝까지 돌리기: "29일에 2시간짜리 교육 잡을 수 있는 교육장 있어?"
   - 바퀴마다 Thought · Action · Observation 이 찍힌다
   - 1 바퀴에서 빈 교육장을 찾고, 그 결과를 보고 2 바퀴에서 그 교육장의 점검 일정을 조회한다
   - 더 부를 도구가 없으면 답을 낸다. ① 모델이 "끝"
4. 한도를 1 바퀴로: 같은 질문 → 모델은 더 하고 싶었지만 우리 코드가 끊는다. ② 하네스가 "그만"
5. 마무리 말: "한도가 없으면 모델이 같은 도구를 끝없이 부를 수도 있습니다. 루프를 돌리는 것도, 멈추는 것도 우리 코드입니다. 실습 5 에서 이 for 문을 직접 구현합니다"

**주의**

- 이 셀은 생각 단계를 다시 켠다. 응답이 느릴 수 있으니 미리 한 번 돌려서 모델을 데워 둔다

## 27장 · 오전 정리

**말할 것**

오전 강의를 정리하겠습니다.

Agent 는 두뇌인 LLM 과 몸인 하네스입니다. Agent 라는 말은 넓게 쓰이고, 모델이 무엇까지 정하느냐로 단계가 나뉩니다. 이건 오후 첫 시간에 다시 봅니다.

LLM 은 다음 말을 예측합니다. 대화도 결국 긴 messages 배열 하나입니다. 그 글은 토큰으로 재고, 컨텍스트 윈도우를 넘으면 잘립니다.

LLM 은 도구를 실행하지 않습니다. 고를 뿐이고, 실행과 통제는 하네스의 몫입니다. MCP 는 그 도구를 꽂는 규격입니다.

고르고, 실행하고, 결과를 보고 다시 고르는 반복이 ReAct 루프입니다. 그리고 그 루프를 돌리고 멈추는 것도 하네스입니다.

이제 이걸 직접 구현해 보겠습니다.

## 37장 · 실습 7 · 사람 승인

**말할 것**

마지막 실습입니다. 지금 Agent 는 조회만 합니다. 이번에는 모자라는 부품을 상급 부대에 청구하는 도구를 줍니다. 그런데 청구는 되돌리기 어렵습니다. 그래서 실행하기 직전에 사람에게 묻게 합니다.

할 일은 두 가지입니다.

첫째, request_part 도구를 더합니다. 부품번호와 수량을 받고, 청구번호를 하나씩 매겨서 돌려주는 함수입니다. system 메시지에 "정비일까지 모자라는 부품은 request_part 로 청구하라" 를 넣습니다.

둘째, runTool 에서 청구 요청이 오면 실행하기 직전에 readline 으로 y / n 을 묻습니다. y 면 실행하고, 아니면 실행하지 않고 "담당자가 청구를 승인하지 않았습니다" 를 결과로 돌려줍니다. 사람의 답을 기다려야 하니 runTool 은 async 가 되고, 루프에서는 runTool 앞에 await 만 붙입니다.

성공하면 [사람] PN-4471 1개를 청구할까요 가 뜨고, y 를 누르면 청구번호 REQ-0001 이 나옵니다. n 을 누르면 청구하지 않고, 모델은 그 사실을 보고 답합니다.

(풀이 뒤)

21장에서 도구 실행은 우리 책임이라고 했습니다. 권한이 있는 요청인가, 위험하면 사람에게 승인받기. 그게 runTool 안의 이 if 하나입니다. 루프는 await 한 단어 말고는 바뀌지 않았습니다. 모델은 청구하겠다고 요청만 했고, 실제로 청구할지는 사람과 우리 코드가 정했습니다.

거절해도 프로그램은 멈추지 않습니다. 거절했다는 사실도 결과로 돌려줍니다. 모델은 그걸 보고 "청구하지 않았다" 고 답합니다.

오전은 여기까지입니다. 프레임워크 없이 Agent 를 만들었습니다. 그런데 이 y / n 은 답이 올 때까지 프로그램이 켜져 있어야 합니다. 담당자가 점심 먹고 와서 답하면 어떻게 될까요. 오후에는 이 루프를 LangGraph 로 옮기고, 이런 기능들을 하나씩 더해 보겠습니다. 점심 맛있게 드시고 1시에 뵙겠습니다.

**주의**

- 실제 모델(qwen3-32b)로 준비하면서 돌려 봄: PN-4471 1개를 청구한 뒤, 재고가 3개 있는 대체품 PN-7731 까지 청구하려고 했다. "모델이 틀린 청구를 하려고 할 때 사람이 n 으로 막는다" 를 보여 주기 좋은 장면이다
- 터미널에서 직접 돌려야 y / n 을 칠 수 있다. VS Code 의 실행 버튼이나 출력 창으로는 입력이 안 된다
- 오후 첫 장(사람 답을 기다리려면)이 이 실습의 y / n 으로 시작한다. 이어서 말하면 자연스럽다
